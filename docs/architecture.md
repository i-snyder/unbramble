# UnBramble — Architecture

Agent-facing reference: the settled design, the invariants that must never be silently traded away, and the correctness findings confirmed against real Unity output and adversarial review. This is the doc to read before touching the scanner, parser, store, or liveness code. History of how these decisions were reached lives in git history; this doc states only what's true today.

## What this is

UnBramble is a standalone, single-binary CLI (`unbramble`) that builds a unified dependency graph of a Unity project — GUID/asset references (prefabs, scenes, materials, shaders, UI Toolkit, Addressables, …) plus C# semantic analysis (Roslyn) — so an AI coding agent (or a human) can ask "what does this touch / what touches this" across the static reference forms UnBramble models instead of reconstructing the picture by grepping and manual reading.

## Non-negotiable invariants

- **Correctness is the only primary goal.** Token/context efficiency matters only instrumentally. Never trade correctness for speed, cost, or token efficiency — if a slower or more expensive query gets a more correct answer, that's the right trade, always.
- **Asymmetric risk (the single most load-bearing rule in this codebase).** A false positive ("this is provably dead / safe to delete" when it isn't) can break a shipped game and is unacceptable. A false negative ("I can't tell") only costs a deeper look and is fine. On any ambiguity, always default to "cannot prove" — never promote an unprovable case to a deletion candidate. This rule is the reason confidence labels can only ever be *downgraded* by ambiguity, never upgraded by a heuristic.
- **Freshness invariant: never wrong, only sometimes slower.** The index may be slow to answer; it may never silently answer from stale data.
- **One binary.** The end user installs and runs `unbramble` and nothing else. Embedding libraries (Roslyn, SQLite) at build time is fine; requiring a separately installed/updated tool (Rider, ReSharper, CodeGraph, etc.) is not — an agent can still use another tool *alongside* UnBramble on its own judgment, but UnBramble never relies on one being present.
- **Not limited to deletion scenarios.** Surgical refactoring in tangled legacy code needs this as much as cleanup passes do.

## Not depending on (evaluated and rejected as runtime dependencies)

- Rider / JetBrains plugins — no Rider build, or no usable asset/C# graph for this purpose.
- ReSharper / Rider / `resharper-unity` — design reference only, never an installed or runtime dependency. Its Apache-2.0 licensing and the runtime dependency licenses are recorded in `THIRD-PARTY-NOTICES.md`.
- CodeGraph (`@colbymchenry/codegraph`, tree-sitter-based) — syntactic-only, no semantic resolution, doesn't clear this project's correctness bar. Roslyn does real semantic analysis (type/overload/generic resolution); UnBramble only needs one language, so it doesn't need tree-sitter's multi-language trade-off.

## Unity serialization primer (facts about Unity, not design choices)

- Every asset (and folder) under `Assets/` and embedded packages has a sibling `<name>.meta` containing `guid: <32 lowercase hex>` — the asset's identity.
- Text-serialized assets are Unity YAML: multi-document files with headers `--- !u!<ClassID> &<fileID>` (fileIDs can be negative; a real, common variant has a trailing ` stripped` token for stripped prefab-instance overrides — a parser that doesn't tolerate it misattributes every ref in those documents).
- A cross-asset reference looks like `{fileID: 2100000, guid: 8b5e4f9c…, type: 2}`. References without `guid:` are internal to the same file.
- Script attachment: `m_Script: {fileID: 11500000, guid: <guid of Foo.cs.meta>, type: 3}`.
- A component's owning GameObject is a same-file ref `m_GameObject: {fileID: G}`; a GameObject's name is `m_Name:` in its own `!u!1` document. Together these let refs be annotated with human-readable GameObject names.
- UnityEvent persistent calls serialize the bound method name in plain text next to the target ref (`m_Target: {…}` + `m_MethodName: Jump` in the same `m_Calls` entry). **`m_Target` never references a MonoScript** — for a cross-asset binding it's `{fileID: <component>, guid: <containing asset — a prefab/scene>}`; for the common same-asset case (button and handler in one prefab) it's a bare fileID with **no guid at all**. Type selection for the bound method can only come from the separate `m_TargetAssemblyTypeName: Foo, Assembly-CSharp` field (Unity 2019.1+), never from `m_Target`'s guid.
- UI Toolkit (`.uxml`/`.uss`/`.tss`) uses **two** reference forms — see the matrix below; USS's `resource("…")` form is a documented exclusion.
- `.meta` files are both identity source *and* reference source (importer remaps).
- Special guids: all-zeros = null (skip); `…e000…`/`…f000…` = Unity built-ins (display as "(Unity builtin)"; excluded from unresolved/broken accounting).
- **Two distinct GUID encodings exist and must not be confused:** plain 32-hex (the real AssetDatabase guid) vs. dashed UUID (`b1fb53e3-1ca7-…`) — Shader Graph/VFX Graph's *internal* node/property identity, present dozens of times per file. Only the first is ever a cross-asset reference.

### GUID edge coverage matrix (must-catch forms, confirmed against real Unity output)

| Edge | Serialization form |
|---|---|
| Prefab/Scene/SO → script | `m_Script: {fileID: 11500000, guid: X, type: 3}` (plain YAML) |
| Prefab → nested prefab | `PrefabInstance` doc, `m_SourcePrefab: {fileID: 100100000, guid: X, type: 3}` |
| Renderer → material | `m_Materials:` array elements |
| Material → shader / texture | `m_Shader:` / `m_TexEnvs` → `m_Texture:` (plain YAML) |
| **ShaderGraph → texture/asset** | JSON-in-JSON with **backslash-escaped quotes**: `"{\"texture\":{…\"guid\":\"X\"…}}"` — a bare-quote regex silently misses every one of these |
| ShaderGraph internal IDs (must NOT index) | dashed UUID `"m_GuidSerialized": "b1fb53e3-…"` — never a cross-asset ref |
| asmdef → asmdef | `"references": ["GUID:0123…"]` |
| **asmdef → precompiled plugin assembly** | `"precompiledReferences": ["Vendor.dll"]` — a bare FILE NAME, no guid and no path anywhere; invisible to the guid regex, so it needs its own extraction and its own table (see `dll_refs` below) |
| UnityEvent → method | guid/fileID ref + adjacent `m_MethodName:` + `m_TargetAssemblyTypeName:` |
| UI Toolkit → asset (guid form) | `guid=X` URL query parameter |
| UI Toolkit → asset (path form) | `src="…"`, `url(…)`, `@import` — no guid at all |
| Any asset → registry package asset | Normal `guid:` form; target lives under `Library/PackageCache` |
| Addressables → asset | `AddressableAssetSettings.asset`'s `m_GroupAssets` (ordinary `{fileID,guid}` refs); each group asset's `m_SerializeEntries[].m_GUID` (**`m_GUID`, not `m_AssetGUID`** — confirmed against real output, see Liveness section) |

## GUID/asset graph indexer

### Project detection & config

- **No required path argument.** Walk up from cwd looking for `ProjectSettings/ProjectVersion.txt`, like `git` walks up for `.git/`. `-p/--path` overrides the walk's starting point.
- Optional `unbramble.json` at project root; sensible defaults: roots `["Assets", "Packages", "LocalPackages", "ProjectSettings"]`, excluded dirs (`Library`, `Temp`, `obj`, `Logs`, VCS dirs, `.unbramble`), DB at `.unbramble/unbramble.db` — a project-root state directory, not inside `Library/` (see "State directory: `.unbramble/`, not `Library/`" below for why).
- **`Library/PackageCache` is scanned identity-only** (parse `.meta` guids into the identity map; never parse package internals as reference sources). Without this, every URP/TextMeshPro/Input System reference reports as UNRESOLVED. Not watched in real time — refreshed on sweep/explicit reindex only.
- Startup assertion: `ProjectSettings/EditorSettings.asset` must show Force Text (`m_SerializationMode: 2`); fail fast with a clear error otherwise.

### Scanner

- Enumerate roots recursively, **following junctions/directory symlinks** (.NET skips reparse-point recursion by default — must be deliberate), deduping by canonical real path, tolerating dangling links with a warning (real projects have them; never crash). Root-level junctions are scanned with bounded parallelism (the main fan-out point on large real projects — several disjoint package trees hanging directly off `Assets/`); the ordinary root walks serially first so a directory reachable without a link keeps precedence, and output ordering stays deterministic regardless of scheduling.
- Store paths project-relative with forward slashes, *as seen through the junction*; persist the real-root → project-prefix mapping (the watcher, running in a different process later, must rewrite real-path events back to project paths using the *same* mapping, not a recomputed one).
- **Mirror Unity's own hidden-asset rules** (dot-prefixed names, `~`-suffixed folders like `Samples~`, folders named `cvs`, `.tmp` files) or the index diverges from what Unity itself sees — package `Samples~` folders ship real assets with real `.meta` files.
- Files of interest: every `*.meta` (identity); text-serialized asset extensions (`.prefab .unity .asset .mat .anim .controller … .shadergraph .vfx .uxml .uss .tss` etc.) as reference sources; `ProjectSettings/*.asset` as guid-less reference sources; `.cs` files for the C#/Roslyn side. Binary assets participate as targets via their `.meta` only.

### Parser

- Line-streaming (never load whole files — scenes can be hundreds of MB), single pass per file.
- One regex covers all guid serialization forms:
  ```
  (?i)(?:guid(?:\\"|")?:\s*(?:\\"|")?|guid=)([0-9a-f]{32})(?!\w)
  ```
  Handles plain YAML, plain JSON, escaped-JSON-in-JSON Shader Graph form, and the UI Toolkit `guid=` form in one pattern; excludes dashed UUIDs by construction (32 bare hex only). Normalize captures to lowercase. Under NativeAOT, use `[GeneratedRegex]`, never `RegexOptions.Compiled` (the latter silently degrades to interpreted matching).
- Lightweight streaming state (not a real YAML parser): track document boundaries (`--- !u!<ClassID> &<fileID>`, tolerating ` stripped`) so every ref is tagged with the component doing the referencing; capture GameObject names and component→GameObject links; a small bounded lookahead captures `m_MethodName`/`m_TargetAssemblyTypeName` next to UnityEvent target refs.
- UI Toolkit path-based refs get a second small extraction pass. **Store them unresolved and resolve at query time** against current file paths — never bake a resolved guid in at parse time (a baked guid goes stale exactly when the *target* moves, making the tool actively wrong — this design error was caught and redesigned during review; don't reintroduce it). Query-time resolution also makes broken path-refs fall out for free.
- Filtering: skip the null guid and self-references; **store unknown targets anyway** (they surface as unresolved/broken/external — dropping them hides real breakage).

### Store (SQLite, WAL mode)

- `files(id, path UNIQUE COLLATE NOCASE, guid NULLABLE, kind, mtime, size)` — one row per asset; guid nullable because source-only files (`ProjectSettings/*`) and not-yet-imported files are real graph nodes.
- `refs(source_file_id, target_guid, line, context, source_classid, method_name, target_type_name, property_path)` — guid-based edges. `property_path` (v7) is the best-effort dotted serialized-field path of the referencing line (`m_Settings.m_VolumeProfile`, `m_Materials[2]`, `m_OnClick.m_PersistentCalls.m_Calls[0].m_Target`), tracked by `YamlPropertyPathTracker`'s indent/key stack during the YAML pass — display metadata only (never queried, joined, or fed into confidence; a wrong path can mislabel an edge's field but can never add/drop/misresolve the edge), which is why best-effort is acceptable here and nowhere else in the parser. NULL for meta/JSON/UI-Toolkit refs. Component + line without the serialized field still forces a Unity-API round trip, which is why this display metadata exists.
- `path_refs(source_file_id, target_path, line, context)` — UI Toolkit path-based edges, unresolved.
- `dll_refs(source_file_id, target_name_raw, target_name_norm, line, context)` (v8) — `.asmdef` `precompiledReferences` entries: a managed plugin assembly referenced by *file name*, which is how Unity itself resolves them. Neither existing edge table can hold one (`refs` is guid-keyed; `path_refs` resolves against `files.path`, which a bare file name never matches — storing it there would make every such edge look permanently broken). Name → file resolution happens at query time, same rule as `path_refs`. **Deliberately NOT a branch of `all_refs`**: matching a bare name against `files.path` needs a leading-wildcard `LIKE` that no index can serve, and `all_refs` is read by every query — one unindexable branch there would tax the whole verb set to serve a handful of rows. Merged in C# at query time instead, exactly like UnityEvent links, which are also real edges living outside the view. The common direction is cheap and indexed (`who-uses <dll>` is a lookup on `target_name_norm`); only the rare forward direction (`uses <asmdef>`, `stats --unresolved`, the liveness seed) pays the unindexed scan, for the few names on one asmdef. Confidence follows Unity's own rule: a name matching exactly one file is `proven`; two or more files sharing it is the case Unity errors on, so every candidate is surfaced at `advisory` — downgraded on ambiguity, never guessed. Without this table, an asmdef reference to `VendorPlugin.dll` returns zero referencers and can let a referenced plugin assembly appear in `provenDead`.
- `roots(real_path, project_prefix)` — persisted junction mapping.
- `gameobjects` / `component_gameobject` — display-name resolution tables.
- `name_hints(id, source_file_id, name, kind, line, type_name)` — negative-evidence names for liveness screening (see below); **not an edge store** — no targets, never walked/joined into any closure or `who-uses` result.
- `build_reachable_cache(file_id)` + singleton `build_reachable_state(valid, config_key, graph_generation)` (v10; cache introduced in v9) — persisted result of the screen-free reachability walk used by query annotations. Any file/reference/symbol graph mutation invalidates it and advances the generation in the same transaction; a changed liveness allowlist misses by `config_key`; publication claims the expected generation before replacing rows, so a computation racing a writer cannot revalidate stale derived state. The next consumer recomputes the complete fixed point atomically. This is a derived performance cache, never a source of truth: it can be absent or invalid and only make the next query slower. One large-project measurement changed an unchanged-project missing-reference query from 8.75s to 176ms.
- An `all_refs` view unions both asset edge tables, resolving a `target_file_id` and carrying a `kind` (`'guid'`/`'path'`) discriminator. A separate `cs_file_refs` view projects Roslyn `symbol_refs` down to file→file edges at query time; `unified_walk_edges` unions the two — see Graph unification below.

**The graph walk is keyed on `files.id`, not on guid — this is a correctness finding, not a style choice.** Guid-less files are full graph nodes: referencers, targets, *and* interior nodes of a transitive walk. A guid-keyed walk structurally cannot represent them. The guid branch's join against `files` must be a LEFT JOIN so unresolved/external guid refs still surface in output. "Walkable" and "has a guid" are orthogonal facts about an edge.

Other store lessons: transitive queries as a recursive CTE over the walk view (two steps — a recursive closure walk, then a separate non-recursive display query with `MIN(depth)` dedup; a single-query version silently drops guid-less referencers, and `UNION` does not terminate cycles — only a depth cap does). Apply deletions before insertions within a diff batch (renames otherwise look like guid collisions). On a guid collision during incremental update, check whether the existing row's path still exists on disk — if not, it's a move, not a collision. Real (both-on-disk) collision warnings compact past a small inline cap into one counted line pointing at `stats --collisions`; the detail is derived live from `files` on demand, never persisted to a side artifact that could go stale. Batch writes in transactions; `PRAGMA busy_timeout` must be installed before any lock-taking pragma; a current-schema store open is read-only (no unconditional DDL or metadata refresh); every finite mutation owns `.unbramble/index-writer.lock` for its full lifetime. That lock is separate from the lifetime-long `watcher.lock`, so WAL readers remain available and an explicit writer only waits for the current watcher batch, not for the watcher process to exit. Under NativeAOT, `Microsoft.Data.Sqlite` needs an explicit `SQLitePCL.Batteries_V2.Init()`.

### Freshness: incremental refresh + background watcher

#### State directory: `.unbramble/`, not `Library/`

Everything this feature owns on disk — the SQLite DB, the watcher heartbeat, the single-writer lock, the watch-status snapshot, and the two auto-spawn marker files — lives under a project-root `.unbramble/` directory (`UnBramblePaths`), not under Unity's own `Library/`. It used to live under `Library/UnBramble/`; that stopped being safe once the auto-spawn watcher (below) started running detached and hidden in the background. That watcher holds an exclusive `FileShare.None` handle on its lock file plus open SQLite handles on the DB — both under whatever directory this state lives in. With state under `Library/`, the standard Unity troubleshooting move ("close Unity, delete `Library/`, reopen — it'll regenerate") started failing with an undiagnosable "the folder is in use" error, caused by a background process the user has no reason to suspect is even running. A project-root `.unbramble/` directory makes that workflow always succeed again, with zero data loss: the watcher's own `FileSystemWatcher`s are scoped to `Assets`/`Packages`/etc., never `Library/`, so wiping `Library/` was never actually necessary to drop for correctness — only for this one avoidable collision. `.unbramble` is also added to `DefaultExcludeDirs` as cheap defense (the default scanner roots never include the project root, so this shouldn't matter today, but a user-configured root could include it) and, on `init`, gets its own ignore-file setup (git/Plastic, plus a self-ignoring `.unbramble/.gitignore`) — see the CLI section below.

There are now two lock scopes in that directory: `watcher.lock` elects one long-lived watcher, while `index-writer.lock` serializes each finite SQLite mutation across watchers, explicit indexes, and inline query sweeps. Lock files are never stale state to delete; the OS-owned handles release on process death.

Governing invariant: **never wrong, only sometimes slower.**

- **Pull (always correct):** any CLI invocation stat-sweeps all in-scope files (metadata only), diffs against the DB (new → parse; changed → rebuild that file's rows across all derived tables; missing → cascade delete), then queries. Skipped when a fresh watcher heartbeat shows a live watcher already owns freshness.
- **Push (primary when running):** a detached watcher worker with one `FileSystemWatcher` per real root (they don't traverse reparse points), debounced ~1s, writing a heartbeat file per cycle. An asset and its `.meta` are always reparsed as one unit.
- **A heartbeat is only trusted when its schema stamp matches the reader's `CurrentSchemaVersion`** (`{"pid","utc","schema"}`; a pre-stamp heartbeat parses as schema 0, never trusted). Found by reasoning through the first schema-bump upgrade: an old-binary watcher keeps heartbeating right through the upgrade while the new binary's open drops and rebuilds the store — trusting that heartbeat would answer from an empty store, silently. A fresh-but-mismatched heartbeat also means the lock holder can *never* become trustworthy, so queries sweep alongside it instead of waiting (the watcher lock only prevents duplicate work — SQLite WAL + busy_timeout make the concurrency safe) and tell the user to run `unbramble stop` to retire the old watcher.
- **Single active watcher, enforced:** exclusive `FileShare.None` lock file (`.unbramble/watcher.lock`); redundant workers exit successfully instead of piling up behind the owner (the OS releases the handle on process death — no stale-lock logic needed). On startup: start watchers buffering *first*, then catch-up sweep, then drain — sweeping before watching leaves an unwatched gap that the heartbeat then vouches for.
- **Self-heal:** a periodic full stat-sweep backstop (default ~5 min) regardless of events, plus an immediate resync on `FileSystemWatcher`'s `Error` (buffer-overflow) event. Directory renames/deletes are a known self-heal-only gap (one event fires, none for descendants).
- **Monitoring:** `unbramble monitor` ensures a detached worker exists, then polls its status file for live progress. Ctrl+C closes only the monitor; the worker continues until its idle timeout or `unbramble stop`. The monitor presentation never affects graph correctness.

### Self-verifying freshness: the deliberate alternative to a connect-time trust window

**Every query re-proves its own freshness — it never trusts a cache.** `EnsureFresh` (`UnBrambleEngine.cs`) runs on every single query invocation: it checks the watcher heartbeat and, if stale or absent, runs an inline sweep before answering, and reports which path it took via the `freshness: ...` stderr line (`--verbose`). This is deliberate and is the reason UnBramble does not need — and explicitly rejects — a "reconcile once when a session/connection starts, then trust it" model the way some other tools (e.g. an MCP server with connect-time indexing, or a long-lived agent session that indexes once at startup) use. A connect-time trust window is only as good as its last reconciliation: if the project changes after that point and before the next reconnect, every query in between silently answers from stale data, with no mechanism to notice or say so. Self-verification on each call closes that gap structurally — there is no window in which UnBramble can be fooled by a stale cache, because there is no cache it trusts without checking. The cost is bounded and stated up front: a query is either instant (fresh heartbeat) or pays for a sweep and says so, never silently wrong.

**A slow inline sweep is never silent.** A cold-cache first sweep can still take tens of seconds, so any sweep that runs longer than ~1.5s starts reporting: a one-line "sweeping the index inline" header, scan progress every ~10s, each post-scan phase boundary (diff apply / reference reparse / C# analysis) — every line stamped with elapsed time — plus a keepalive ("still running C# analysis -- not stalled") whenever nothing else has printed for 15s. Fast sweeps print nothing — see `Program.SweepProgressPrinter`. `init`/`index`/the zero-args home command use the live ANSI renderer (`BrambleProgressRenderer`) instead whenever the terminal supports it; the plain printer is the shared fallback, fed by the identical RunIndex callbacks. **Stream routing:** in text mode all freshness/progress/warning output goes to STDOUT, ahead of the results — agent harnesses merge the stdout/stderr pipes with no cross-stream ordering guarantee, so separate streams can display in the wrong order. `--json` keeps diagnostics on stderr so stdout's JSON contract stays pure. verify-all's watch-smoke step reads the freshness line accordingly.

**Explicit rejection: no per-message/per-turn ambient hook.** UnBramble must never gain a freshness check that runs automatically on every agent turn regardless of whether a query actually happened — e.g. a `UserPromptSubmit`-style hook, or any mechanism that fires on a timer or message boundary rather than inside a deliberate query. This was evaluated and rejected because that shape of check is exactly what makes tools like CodeGraph's session-scoped reconciliation fragile in practice: it can silently time out on a large project with no visibility into what happened, burning agent context on every turn for a check nobody asked for at that moment. UnBramble's freshness checks only ever run inside a deliberate query, are bounded by that query's own sweep (never open-ended), and always report their outcome on that query's own output. If a future surface (see the MCP note below) is ever added, this rule still applies to it unchanged.

### Background watcher lifecycle

Self-verification (above) already guarantees every query is *correct*. The background worker closes the remaining speed gap without weakening that guarantee:

- **Trigger:** `unbramble monitor` always attempts an idempotent worker start before displaying status. Query verbs also start one after an inline sweep (subject to `watch.autoStart`) so the next query can use a fresh heartbeat. The actual `watch-worker` verb is a hidden process entry point, not user-facing CLI.
- **Launch mechanics are load-bearing** (found live against a large real project): the child is launched with `UseShellExecute = true` (ShellExecuteEx, hidden window), NOT `UseShellExecute = false`. The `false` path makes .NET call `CreateProcess` with `bInheritHandles=TRUE`, which duplicates every inheritable handle of the query process into the long-lived watcher — including the *caller's* stdout/stderr pipe write-ends when a script or agent captures the query's output. The caller then never sees EOF after the query exits (the watcher still holds a duplicated write handle) and hangs indefinitely on a query that actually finished; verified with a pipe-captured repro. Redirecting the child's own std streams does NOT fix it — the leak is the wholesale handle duplication, not the child's std handle assignment. ShellExecuteEx inherits nothing. The worker also swaps `Console.Out`/`Console.Error` for `TextWriter.Null`; its observable surface is `.unbramble/watch.status.json` through `unbramble monitor`.
- **Worker lifetime:** if `WatcherLock` is already held, a redundant worker exits 0 immediately. The owner self-terminates after an idle TTL (`AutoIdleGate`, default ~2 hours) of no fast-path query activity; `EnsureFresh` touches `.unbramble/watch.lastquery` whenever a query uses its heartbeat.
- **Crash-loop guard:** before spawning, the query path checks `.unbramble/auto-spawn.lastattempt` (`AutoSpawnPolicy`, default 3-minute cooldown) and skips spawning if the last attempt — regardless of its outcome — was too recent. This bounds retry frequency if a spawned process keeps failing; queries stay exactly as correct either way, just without the speed benefit until a spawn eventually succeeds.
- **Config toggle:** `unbramble.json`'s `watch.autoStart` (default `true`) turns this off entirely for a project. `unbramble init` mentions the default in its first-run output.
- **Fail-safe framing — do not compromise this for cleverness.** At every failure point (spawn fails, spawned process crashes, lock contention, TTL expiry, config disabled), the correct behavior is always "the next query runs its own inline sweep and stays correct, just not instant, and says so via the existing `freshness: ...` line." No code path introduced by this feature ever lets a query trust a heartbeat/marker without going through `EnsureFresh`'s own proof — the two new marker files (`watch.lastquery`, `auto-spawn.lastattempt`) are pure telemetry for this feature and are never consulted by `EnsureFresh` itself.

## C# semantic graph (Roslyn)

Roslyn (`Microsoft.CodeAnalysis.CSharp`, bundled at build time) does real semantic analysis: method calls, type/field references, inheritance, overload/generic resolution, MonoBehaviour lifecycle entry points.

- Compilations are built per asmdef/predefined-assembly unit. **Mode A** (semantic): a generated `.csproj` exists for the unit and parses to ≥1 define/reference — trust it, build a real Roslyn compilation. **Mode B** (syntactic): no usable csproj — parse-only, far blinder (only `inherit` and `call` ref kinds are ever emitted; no `type-ref`, no `member-access`). Any syntactic assembly disqualifies liveness claims (`dead-candidates`) entirely — see below.
- Mode A does **not** cross-check the Unity version on the generated csproj; trust is "csproj present and parses". A *stale* generated csproj can carry wrong scripting-define symbols, which compiles out `#if`'d code and its references — this is why `dead-candidates`' preflight includes a csproj-staleness gate (below), and why a stale csproj on `who-uses`/`uses` adds a `csproj-stale` blind-spot flag rather than silently trusting it.
- Every Mode B unit's reason is persisted too (`assemblies.mode_reason`, schema v6): `no-csproj` (nothing generated yet — the common case, before the project's ever been opened in an IDE), `csproj-unusable` (present but 0 defines/references), `csproj-parse-failed` (malformed XML). Purely diagnostic — `CsModeSelector.Determine` sets it, nothing reads it back into a decision — but it's what lets `who-uses`/`uses`/`stats` name a specific assembly and say *why* instead of just "some assembly somewhere is syntactic". Real feedback that motivated this: a partial-semantic project (package assemblies semantic, the product assembly syntactic because the IDE hadn't been opened yet) returned a silent 0-result `who-uses` on an interface method whose only caller lived in the syntactic assembly — see the name-match fallback below.
- Extraction coverage that liveness soundness depends on (must not regress): generic type arguments in invocation/object-creation expressions (`AddComponent<Foo>()`, `GetComponent<Foo>()`, `CreateInstance<Foo>()`); every identifier/qualified name in type position (casts, `is`/`as`, locals, generics), not just declaration sites; method-group/delegate-conversion references (`AddListener(Helper.Handle)`, `Action f = Helper.Handle`) as normal resolved `call`-kind refs; attribute names on types/methods; string literals passed to known by-name dispatch APIs (`SendMessage`, `BroadcastMessage`, `Invoke`, `InvokeRepeating`, `StartCoroutine`, `CancelInvoke`) captured into `name_hints` as negative evidence, never as edges.

## Graph unification: one seam, no third edge store

`who-uses`/`uses --transitive` cross between the asset graph and the C# graph through a **query-time SQL view**, not a persisted third edge table — both stores keep their own shape, refresh discipline, and deletion cascades:

```sql
-- symbol_refs projected to file->file edges; doc_id -> declaring-file resolution happens
-- HERE, at query time (the same "never bake a resolved id at parse time" lesson as path_refs).
CREATE VIEW cs_file_refs AS
SELECT sr.source_file_id, 'cs' AS kind, sr.target_doc_id AS target_key,
       tgt.file_id AS target_file_id, sr.line, sr.ref_kind, sr.confidence
FROM symbol_refs sr
JOIN symbols tgt ON tgt.doc_id = sr.target_doc_id
WHERE tgt.file_id IS NOT NULL AND tgt.file_id != sr.source_file_id;

-- The relation both who-uses' transitive walk AND dead-candidates' liveness propagation walk.
CREATE VIEW unified_walk_edges AS
SELECT source_file_id, target_file_id FROM all_refs WHERE target_file_id IS NOT NULL
UNION
SELECT DISTINCT source_file_id, target_file_id FROM cs_file_refs;
```

- **One hop = one file-level edge, regardless of kind.** `Player.prefab —guid→ Foo.cs` is depth 1; `Foo.cs —cs→ CoreUtil.cs` from there is depth 2. Symbol-level precision is *annotation* on a file edge, never extra depth — this keeps `--depth N` meaning one consistent thing.
- **Confidence is derived at the query layer, never stored.** Three labels: `proven` (guid ref resolved to a file; exact-normalized-match path ref; semantic Roslyn resolution; a strictly matched UnityEvent link), `advisory` (syntactic/text-coincidence resolution; ambiguous overload or inherited UnityEvent match; a file-level fact surfaced for a symbol-level query; a guid-less same-asset UnityEvent binding), `speculative` (a who-uses-**symbol** query's name-match fallback: when any syntactic assembly exists, `symbol_refs` rows with `confidence='syntactic'` whose target doc-id's trailing identifier matches the queried symbol's simple name are surfaced as leads — never a real join, since a syntactic target doc-id is text-derived and carries no type information). Labels can only be **downgraded** by ambiguity, never upgraded by a heuristic — the one exception granted to `speculative` is answer-level aggregation: it's ignored in the weakest-link computation (`EdgeConfidence.AnswerLevel`) unless it's the *only* tier present, so a genuine proven/advisory result is never dragged down by a speculative lead sitting alongside it.
- **Answer-level confidence is the weakest edge on the path** — a transitive chain crossing one advisory hop is an advisory answer, full stop. (Speculative is the one carve-out, immediately above.)
- **Every answer that can depend on C# carries a `blindSpots` array** (fixed enum: `string-path-loading`, `reflection`, `syntactic-assemblies-present`, `addressables-unconfirmed`, `depth-truncated`, `csproj-stale`) so an answer that could be wrong for a reason the tool knows about says so on every answer, not just in docs. When `syntactic-assemblies-present` fires, the answer also carries a `syntacticAssemblies` summary (total count + a capped named sample with each assembly's `mode_reason`, plus a fixed remediation hint) — named attribution, not just the anonymous flag; the query footer/JSON and `stats` (full unnamed-cap list) all read from the same `GetSyntacticAssemblyDetails` store accessor. A who-uses-symbol answer with no proven/advisory result (only speculative leads, or nothing) while syntactic assemblies exist also sets `possibleFalseNegative` — an explicit "this silence might just be the syntactic blind spot, not a real absence" signal, since the whole point of `syntactic-assemblies-present` is that a 0-result answer here is not proof of absence. Strictly serialized missing-reference queries and reverse answers with neither a C# or UnityEvent edge nor `possibleFalseNegative` suppress C#-only flags, attribution, remediation, and sweep warnings: those cannot change the displayed asset answer, and presenting them as relevant remediation caused agents to interrupt successful audits. `--verbose` remains the escape hatch for freshness diagnostics.
- Unresolved refs and unresolved doc_ids stay in their own unresolved bucket, never given a confidence label — confidence is never a place to hide breakage.

## Liveness / `dead-candidates`: forward reachability, file-granular

Forward reachability from a defined root set — **never** "nothing references this" (a much weaker claim). Roots are file nodes, materialized at query time from path rules and existing edges (no new tables):

- **Every non-identity-only file under `ProjectSettings/`** is a root. Because `ProjectSettings/*.asset` are already parsed as guid-less reference sources, this alone covers Build Settings scenes (`EditorBuildSettings.asset`) and Player Settings preloaded assets (`ProjectSettings.asset`'s `m_PreloadedAssets`) with zero new parsing. Disabled Build Settings scenes are still roots (conservative — a disabled scene and its subtree are never reported dead).
- **`Resources/`**: any file whose path contains a `/Resources/` segment (Unity's own rule). **`StreamingAssets/`**: any file under `Assets/StreamingAssets/`. Both mitigate the string-path-loading blind spot directly.
- **Addressables**: gated behind a version-confirmed detector (see "Known gaps" below) — until confirmed for the project's resolved Addressables version, liveness is **entirely unavailable**, not degraded, for any project that has Addressables installed.
- **C#-side unconditional entry points**: `[RuntimeInitializeOnLoadMethod]`, `[InitializeOnLoadMethod]`, `static Main` in semantic-mode assemblies. MonoBehaviour lifecycle methods are deliberately **not** unconditional roots (that would mark every MonoBehaviour live and gut the flagship use case) — they become live by ordinary reachability once their containing file is live via any other path.

Edges that live outside `unified_walk_edges` — matched UnityEvent links, and asmdef→plugin-assembly `precompiledReferences` edges — are seeded into the propagation workspace (`seeded_extra_edges`) by one shared `UnBrambleEngine.SeedExtraWalkEdges` helper that *both* fixed points call (`dead-candidates`' and the build-reachable tag's). One helper, not two call sites: propagating over different edge sets in the two directions would break the coherence guarantee below, since `who-uses` could then show an edge the liveness walk never crossed.

**The reachability computation is file-granular, over exactly the `unified_walk_edges` view `who-uses` walks — one edge set, two directions.** This is both the safety fix and the simplification over an earlier symbol-granular design that was rejected in adversarial review: a live file's field/property/ctor-typed dependency was proven dead because symbol-level activation never propagated its outgoing refs. Under file granularity, any live file's *entire* set of outgoing resolved edges makes their targets live — deliberately over-approximate, the direction the asymmetric-risk invariant demands. This makes a strong coherence guarantee **hold by construction, not by audit**: no file emitted as `provenDead` can simultaneously be the target of a resolved edge from a live file — because `dead-candidates` and `who-uses` read the identical view in opposite directions.

**Referenced-by-convention files are excluded from the candidate universe outright** (never proven, never advisory): `*.asmdef`, `*.asmref`, `link.xml`, `csc.rsp`, and any embedded package's `package.json` — Unity consumes these by convention, not by reference, so the graph structurally cannot reach them, but deleting one silently restructures compilation.

### Build-reachable tag on `who-uses` (screen-free, ungated reuse of this walk)

Proven referencers can still be irrelevant test/dead content. Every `who-uses` answer now tags each referencer with whether its source file is forward-reachable from the liveness roots (`UnBrambleEngine.ComputeBuildReachablePaths` — same seeds, same `live_files` propagation, but NO screens and NONE of dead-candidates' gates). Missing references also carry the source asset's reachability and support `--build-reachable-only`, which is where the tag pays off most in noisy audit output. That's sound because the tag only ever backs a POSITIVE claim: `[build-reachable]` is proven; the other case renders as `[not proven build-reachable]` (JSON `buildReachable: false`) — absence of proof, never "unreachable". Missing cs edges (syntactic assemblies) or an unconfirmed Addressables version can only *under-report* reachability, which is the safe direction for this tag — the same asymmetric-risk rule, pointed the other way. Two deliberate divergences from dead-candidates' roots: screens don't run (they exist to keep maybe-live files off the dead list — seeding them here would invent reachability), and the Addressables root seeds whenever Addressables is detected at all (unconfirmed can only cost coverage). The fixed point is one recursive SQL CTE rather than one command/round-trip per propagation level, then persisted in the versioned derived cache described above.

### Screens: seed liveness, don't just suppress

A candidate that fails to clear every screen is **seeded into the live set** (not merely hidden from output) and reported as `advisoryDead` with its reason — seeding matters because a maybe-live file's own dependency chain must survive with it, exactly like the user-supplied allowlist (`unbramble.json`'s `liveness.allowlist`, which uses the identical seed semantics).

| Screen | Rule |
|---|---|
| Path-ref name collision | an unresolved *path-kind* ref whose final path segment matches the candidate's filename |
| Syntactic-text collision | an unresolved `symbol_refs` row whose trailing identifier matches a symbol the candidate declares |
| Name-hint collision | a `name_hints` row from a **live** file (SendMessage/Invoke literals, animation-event names, guid-less UnityEvent bindings) matching a candidate method name |
| Attribute screen | the candidate declares a type/method with any attribute outside a curated inert list (`[Serializable]`, `[SerializeField]`, `[Header]`, …) — catches reflection-driven frameworks (custom editors, DI, serializers, test runners) |
| Disabled-region screen | an identifier inside a `#if`-disabled region of a **live** file matches the candidate's declared names — catches wrong-scripting-defines blind spots |
| Interface/virtual-dispatch guard | the candidate implements a **live** interface or overrides a **live** base member — polymorphic calls resolve to the base doc_id, not the implementation's, so it can have zero direct inbound refs while live |
| No-extracted-symbols screen | a `.cs` candidate with zero rows in `symbols` (e.g. a whole-file platform-gated file with no declared symbols the other screens can match against) is treated as advisory by default — closes a confirmed false-`provenDead` gap found on a real project (a whole-file `#if SOME_SDK_ANDROID`-style plugin-define-gated class referenced from a live file's disabled region, with nothing to match it to) |
| Unity-callback guard | a type invoked only through a metadata-only interface (e.g. `ISerializationCallbackReceiver`) or a known Unity callback base class (`AssetPostprocessor` et al.) has no ordinary inbound call edge — screened via a `cs-unity-callback` name hint so it isn't silently proven dead |

### UnityEvent method linking

Type selection for a bound method comes **only** from `m_TargetAssemblyTypeName`  — never from `m_Target`'s guid, which identifies the containing asset, not a script. Cascade: exact single member match in a semantic-mode assembly → `proven`; multiple overloads → `advisory` link to every overload (never guess which one Unity picked); no declared match → walk the project's `inherit` chain upward, any match found this way is `advisory`; no type resolvable or no match anywhere → an unmatched-advisory edge carrying the raw name, and the name enters the liveness screen set. Guid-less same-asset bindings (the common case — button and handler in one prefab) have no resolvable target chain at all; they contribute a `name_hints` row only, and rely on the handler's own `m_Script` attachment for file-level liveness.

### Output contract

`dead-candidates` preflight gates (any failure ⇒ `liveness unavailable: <reason>`, exit 1, **zero candidates emitted** — never a partial/degraded list): Force Text; freshness proven; all assemblies semantic (one syntactic assembly disqualifies the whole run); no Addressables, or Addressables confirmed for the detected version; generated csprojs not stale relative to `Packages/manifest.json`, `ProjectSettings/ProjectVersion.txt`, `ProjectSettings/ProjectSettings.asset`, `ProjectSettings/EditorUserBuildSettings.asset`. All failed gates are listed at once, never just the first.

Scope is **file-level only** — not individual dead methods. Member-level proofs would have to survive by-name dispatch (SendMessage strings, animation events, UnityEvents, reflection), and after every honest screen the proven bucket would be nearly empty; file-level is the flagship "most of this project is removable" case and a much stronger claim. Deferred, not abandoned.

The blind-spots footer is **unconditional output**, every run, both formats — not a flag. The tool's job stops at "provably unreachable by static analysis, blind spots stated" — it explicitly prescribes, and its own output text points at, the workflow that absorbs residual risk: propose a small batch → delete → run the project's own smoke tests → merge if green → repeat.

## Windows Defender exclusion setup: elevation mechanics are load-bearing

`unbramble defender setup` (offered on `init`, see README) elevates once via UAC to add Defender exclusions (`Add-MpPreference`), via `UnBramble.Cli/Defender/DefenderExclusionSetup.cs` + `DefenderSeams.cs` + `DefenderApply.cs`. Three real, live-elevated-run bugs were found here in a row, each one only reproducible on a real machine with real UAC — the same "found live, not guessed" pattern as the auto-spawn watcher notes above:

1. **`ProcessStartInfo.WorkingDirectory` unset.** Both the elevated launch and the `powershell.exe` call it made silently inherited the calling process's own ambient current directory (a non-elevated user's shell CWD, e.g. their project root). Fix: pin `WorkingDirectory` to `Environment.SystemDirectory` on every launch this feature performs (`DefenderProcessLaunchBuilder`) — a fixed, neutral, always-accessible directory with no relation to any project.
2. **Two elevation hops.** The original design elevated `unbramble.exe` itself (a locally built, Authenticode-*unsigned* binary) into a hidden `defender-apply` verb, which then spawned `powershell.exe -EncodedCommand ...` as its own direct child. Collapsed to a single hop: elevate `powershell.exe` directly via `runas`, so its real OS-level parent is the trusted Windows AppInfo service, never the unsigned custom binary. (This was motivated by — and initially suspected to fully explain — Defender ASR/behavior-monitoring rules that target exactly the "unsigned process spawns encoded PowerShell" shape; it turned out not to be the actual cause here, see #3, but removing the unnecessary hop is still correct on its own merits and matches how JetBrains Rider's own Defender-exclusion feature elevates straight to a script.)
3. **`-EncodedCommand` argument length.** Fix #2 alone did *not* resolve the live failure — identical "Access is denied" persisted with a real UAC prompt shown and approved, even from a caller that was already elevated, and regardless of which shell (`pwsh` vs. legacy `powershell`) invoked `unbramble`. That ruled out working directory, parent-process trust, calling shell, and elevation state as variables — and `Get-MpPreference`'s `AttackSurfaceReductionRules_Ids` came back completely empty on the test machine, ruling out ASR specifically. The actual cause: the whole check-then-add-then-verify script was base64-encoded into a single `-EncodedCommand` argument, which for a real multi-entry plan runs several thousand characters (~8,200 measured for a representative plan). `ShellExecuteEx`'s `lpParameters` has a real, documented practical limit around ~2,000 characters — past that it can fail with exactly this "Access is denied"-shaped error, especially combined with the `runas` verb. This explains the 100% reproducibility regardless of every environmental variable tried: a hard technical limit doesn't care about any of them. Fix: write the script to a short-lived temp `.ps1` file (OS temp dir, random name, UTF-8 with BOM, deleted after the elevated process exits) and invoke `powershell.exe -File "<path>" -ExecutionPolicy Bypass` instead — an argument string under 200 characters regardless of plan size, so this can't recur no matter how large a project's exclusion list grows.

The plan-file/result-file contract (`.unbramble/defender-plan.json` / `.unbramble/defender-result.json`, written and read by `DefenderPlanFile`/`DefenderResultFile`) survived all three fixes unchanged: the elevated PowerShell reads the plan and writes the result itself, since stdout can't cross a `runas` elevation boundary (`UseShellExecute = true` precludes redirected streams). If a fourth live failure ever surfaces here, check that contract first — it's the one piece of this feature that hasn't needed to change.

## Known gaps and deliberately deferred work

- **Addressables**: confirmed for **1.21.x, 2.3.x, and 2.8.x** (`AddressablesDetector .ConfirmedRanges`) — see the Liveness section above for provenance per range. Before widening the confirmed range: capture real output from the new version and verify field names against it, don't bump the version constants on changelog reading alone. An unparseable/unrecognized version is treated as unconfirmed by design (the safe default).
- **Member-level dead-code detection** — deferred; file-level is the shipped scope.
- **Multi-build-target define union** (analyzing under several csproj define sets and intersecting deadness) — deferred; the disabled-region screen already closes the safety hole at file granularity for a fraction of the cost.
- **Mode C** (reference reconstruction from `Library/ScriptAssemblies` when no generated csproj exists) — deferred; the syntactic-assembly liveness gate makes its absence honest, not dangerous.
- **MCP wrapper** — deferred; CLI-first, because agents under-use MCP tools relative to CLIs even when instructed to. If built: thin stdio wrapper over the same query layer, versioned JSON envelope, closed enums for `kind`/`confidence`, never a query the CLI can't run identically. **Guardrail, non-negotiable if this is ever built:** every answer must route through the same `EnsureFresh` call the CLI uses and never drop the freshness report — see "Self-verifying freshness" above, which this rule extends unchanged to any future server surface.
- **Indexing performance**: the phase-timing, C#-analysis skip gate, stat-sweep fixes, metadata-reference cache, parallel asset parsing, level-parallel Roslyn, and store-hygiene work have all shipped; the no-change sweep now meets the <2s target on real projects. Still genuinely open: the level-parallel Roslyn scheduler has no width/memory cap and is untested at 159-asmdef scale; cold-cache first-sweep cost is inherent (the watcher heartbeat is the designed answer to this, not a bug to fix); persisted per-assembly compilation artifacts and USN-journal sweeps remain evaluated-and-deferred, not rejected — just not currently justified.
- **`link.xml`-preserved code paths, native plugin callbacks, `Type.GetType(string)`/DI-by-name reflection** — permanent, disclosed blind spots, absorbed by the delete-batch → smoke-test workflow, not by tool confidence.

### Evaluated, not yet built

The correctness items found alongside these requests shipped (`precompiledReferences` indexing, the `cs-refs` UnityEvent merge, `resolve`'s unresolved-guid parity — all three documented above). These remaining usability items stay here so the reasoning survives.

- **`inspect <asset> [--component TypeName]` — reading serialized field VALUES.** The largest remaining gap and the last legitimate reason for an agent to open a `.prefab` by hand: this tool proves which file/line/field references an asset, but a decision can turn on the value in that field (`<_jtacPlatformUnlocked>k__BackingField: 1`, a `_pagePlatformType: 3` prefab-variant override), which a reference-only index cannot answer. Three features of steeply increasing cost, and they should ship in this order, not together: (1) dump a component document's raw fields — tractable today, since the parser already tracks document boundaries and `YamlPropertyPathTracker` already builds the dotted paths, and a bounded query-time read doesn't violate the never-load-whole-files rule; (2) prefab-variant override resolution — the hard part and the dangerous one, because a wrong merge produces a *confidently wrong value*, which is the failure mode the asymmetric-risk invariant exists to prevent, so ship (1) explicitly labeled "no override resolution applied" rather than blocking on it; (3) joining enum ints to their C# enum names — needs schema work first, since `symbols` stores no field types and no enum member values, so there is nothing to join against.
- **Resolved `uses` high-fan-out noise on prefabs.** Missing-reference grouping has shipped (`--summary` / `--group-by-target`, with `--top`), but ordinary resolved dependencies can still include 40+ consecutive `m_Modifications[N].target` rows naming the same source prefab. Two independent cheap fixes remain: collapse per-`PrefabInstance` in the TEXT rendering only (`property_path` is already stored, so grouping by target file + `m_Modifications` prefix needs no schema change — same shape as the existing `Library/PackageCache` collapse, and never silent, never in `--json`); and a target-KIND filter, which `files.kind` already supports. Note `--kind` is already taken on both query verbs for *edge* kind (`guid|path|cs|event|dll`) — a target-type filter needs a different flag name.
- **`who-uses` on a `.cs` mixes asset referencers with the file's own test references** — 18 rows where 17 came from one test file, burying the asset referencers that are usually the point. Grouping cs referencers by referencing file with `--verbose` to expand is cheap and reasonable; the constraint is the "two text renderings must never diverge in *words*" invariant above.

### Re-raised and decided

- **C# caveats on asset-only queries.** A strictly serialized missing-reference answer cannot change when Roslyn coverage changes. Those queries now omit C#-only caveats and sweep warnings unless `--verbose`; reverse lookups omit them when no C#/UnityEvent edge participates and `possibleFalseNegative` is false, including a script GUID whose only answer is a prefab's serialized `m_Script`. This is relevance filtering, not cross-process "once per session" state, so it preserves the freshness invariant.
- **Tombstone index of GUIDs seen in past index states** ("last resolved to X, disappeared around \<date\>"), to turn an unresolved guid from a dead end into an answer. Declined. It introduces a new class of persisted historical state that can go stale and actively mislead — a tombstone naming an asset that has since come back, or was never what the record says — against a store whose governing invariant is *never wrong, only sometimes slower*. The cheap part of the value was delivered instead by `resolve`'s unresolved-guid answer above, which says truthfully what is known ("not in this index") without inventing history. Reconsider only with a design that cannot outlive its own accuracy — e.g. deriving the answer live from VCS history rather than persisting a side table.

## CLI shape

```
unbramble init [path] [--no-agents]  first run: build the index, write AGENTS.md/CLAUDE.md, print watcher setup guidance
unbramble index [path] [--full]    explicit refresh / rebuild
unbramble monitor [path]           ensure the background watcher exists and show live progress
unbramble stop                     stop live unbramble background processes
unbramble defender status|setup|remove [path]   Windows Defender exclusion setup (see README)
unbramble who-uses <path|guid|symbol> [--transitive] [--depth N] [--kind guid|path|cs|event|dll] [--under prefix]
unbramble who-uses --guids <file> [--json|--jsonl]
unbramble uses <path|guid> [--transitive] [--missing-only] [--summary|--group-by-target] [--top N] [--build-reachable-only] [--fail-if-found] [--under prefix]
unbramble audit-assets <paths-file> --missing [--group-by-target] [--top N] [--build-reachable-only] [--json|--jsonl]
unbramble cs-refs <symbol|doc-id>
unbramble resolve <path|guid|name-fragment>
unbramble stats [path] [--unresolved] [--collisions]
unbramble dead-candidates [path] [--json] [--include-advisory] [--kind assets|cs|all]
```

Every verb supports `--help`, `--json` for machine consumption, and `-p/--path` to point at a project without `cd`-ing into it. Query paths normalize `\` to `/` at the engine boundary, so paths copied from Windows tools work identically to Unity-style paths.

**Missing-reference audit workflow:** `uses <asset> --missing-only` returns owner GameObject, component/script, serialized property path, prefab override/source context, `m_Script` classification, and source build reachability for each unresolved link. `--summary` / `--group-by-target` collapses repeated target keys while retaining distinct owner fields/components/objects/source prefabs and counts; `--top N` limits groups; `--build-reachable-only` filters noisy dead/sample sources. `audit-assets <paths-file> --missing` runs the same query for many assets after one freshness snapshot and one reachability load; `uses --missing-only --paths <file>` is an exact alias. `who-uses --guids <file>` does the same for reverse GUID lookups. Batch commands report per-target progress on stderr and support JSONL so automation receives one complete object per target without corrupting stdout JSON.

**High-fan-out scoping:** `--under <prefix>` scopes either query verb to one location (referencers for `who-uses`, dependencies for `uses`; rows without a path on the filtered side are excluded — a location filter only keeps what provably has that location). Independently, `uses`' TEXT rendering collapses `Library/PackageCache/` dependencies to one counted line once they outnumber a small threshold — never silently (the line states the count and both expansion routes), never in `--json`, and never under `--verbose` or an explicit `--under` (scoping IS the expansion request).

**Text output has two renderings, and which one you get is decided by `ConsoleCapabilities.TerminalWidth` alone** (non-null only when stdout isn't redirected, or when `UNBRAMBLE_COLUMNS` forces a width — that override exists because capturing the output is precisely what suppresses the human rendering, so it's the only way to see or test it). A human terminal gets prose wrapped to the width with a hanging indent (`Program.WriteParagraph`, via the ANSI-aware `TextWrap`), blank-line grouping between findings, one blank line above and below the whole invocation (`Main`'s spacer wrapper, so an answer doesn't collide with the shell prompt), and `stats`' key/values padded into an aligned column. A redirected stream gets exactly one unwrapped line per statement, no spacers, no padding — the shape agents and `grep` want, and the shape the CLI text tests assert against.

- **The invariant: layout is human-only, and the two renderings must never diverge in *words*.** Wrapping/padding/spacers are the only permitted difference; anything that changes what is said belongs in both. Making the wrap unconditional would silently break every text assertion in the suite and every agent parsing text output, which is why the gate is a single property rather than a per-call-site decision.
- Layout is deliberately gated separately from color (`SupportsAnsi`): `NO_COLOR` in a real terminal still wants wrapped, aligned prose, just uncolorized. Width is read live (not cached like the color capabilities) because a terminal can be resized under a long-lived `watch`.
- `TextWrap` measures *visible* width — escape codes occupy no columns — and only ever breaks at a space between words, so a line can never end mid-escape-sequence and print the tail as literal garbage.

**Agent discovery: `AGENTS.md` / `CLAUDE.md`.** UnBramble has no MCP server and injects nothing into any agent's context, so a fresh coding-agent session has no way to learn it exists. `init` closes that gap by writing static instruction files at the project root (`AgentInstructionsSetup`): an idempotent, version-stamped, marker-delimited block (`<!-- unbramble:begin/end -->`) upserted into `AGENTS.md` on every run, plus a one-line `CLAUDE.md` shim pointing at it — created only if `CLAUDE.md` doesn't exist yet; if it exists and already references `AGENTS.md` it's left alone, and if it has other content and no such reference it's never touched (a user's `CLAUDE.md` is their own prompt surface). A pre-existing hand-written `## unbramble` section with no markers is migrated into the managed block in place, once. Opt out with `init --no-agents`.

**Exit codes**: `0` = the command/query executed successfully, including when a missing-reference query found broken links; `1` = environment/usage error (not a Unity project, Force Text off, bad args, or `dead-candidates`' liveness-unavailable gate); `2` = query target not found/ambiguous; `3` = findings were present and the caller explicitly requested the CI gate with `--fail-if-found`. Findings are data, not tool failure, unless the caller opts into that policy.

**`resolve` on a well-formed guid that matches nothing is exit 0, not exit 2.** `who-uses`/`uses` already answered an unmatched bare guid gracefully — `ResolveQueryTarget` treats it as a valid target with a null `FileId`, since direct refs by literal guid are still answerable — while `resolve` reported "no match" and exited 2 on the same input. An agent probing an unknown guid's identity reaches for `resolve` *first*, so it hit the error path on a perfectly good question. A 32-hex guid absent from the index is an *answer* ("not in this index — a deleted asset, or one from a package that isn't installed", JSON `unresolvedGuid: true`); a non-guid query that matches nothing is still a failed lookup and still exits 2.

**`cs-refs` reports UnityEvent bindings and carries the standard caveat footer.** It previously read `symbol_refs` alone, so a method whose only caller was a serialized `Button.onClick` binding came back "0 referencers" — with no blind-spots footer either, making it the one unqualified zero the tool could print, and exactly the answer an agent reads as "safe to delete". `who-uses <symbol>` had those bindings all along (`GetEventLinksTargetingDocId` + `GetLocalEventBindingsTargetingDocId`); the two symbol-level surfaces had simply drifted. Both now read one shared `UnBrambleEngine.SymbolEventReferencers` accessor so they cannot drift again. `cs-refs` deliberately stays the *narrower* verb — no declaring-file asset context, no speculative name-match fallback — and its empty answer points at `who-uses`, which asks the wider question, rather than quietly widening itself. Bindings are counted in their own section, never folded into the `symbol_refs` count, so that number keeps meaning what it always meant.

**Cross-cutting rules that apply everywhere in this codebase:**

- NativeAOT compatibility: `[GeneratedRegex]` (never `RegexOptions.Compiled`); explicit `SQLitePCL.Batteries_V2.Init()` at startup; avoid reflection-based serialization for `--json` output (hand-written or source-generated `System.Text.Json`).
- Paths: project-relative, forward slashes; all comparisons case-insensitive; tolerate spaces, brackets, non-ASCII.
- Streaming: never load whole asset files into memory. Line-stream, single pass per file.
- SQLite hygiene: WAL mode, `PRAGMA busy_timeout` on every connection, batch writes in transactions, deletions before insertions within a diff batch.
- Fail loudly, degrade honestly: unknown/unresolved targets are stored and surfaced, never dropped; ambiguity is reported as "can't tell", never guessed away.
- Never assume the target project's VCS is git (Plastic SCM/Perforce are common in Unity shops).
- Performance targets (design scale ~100k files): full index < 60s, no-change refresh < 2s, queries < 100ms. Targets, not license to trade away correctness — see the "Indexing performance" bullet in Known gaps above for what's still open.

## Glossary

- **guid** — Unity's 32-lowercase-hex asset identity, from the sibling `.meta` file. Distinct from **dashed UUIDs** (`b1fb53e3-1ca7-…`), which are Shader Graph/VFX internal IDs and never cross-asset references.
- **fileID** — identity of a document *within* one Unity YAML file (`--- !u!114 &8395…`); can be negative; can carry a trailing ` stripped` token.
- **identity-only file** — a file (e.g. under `Library/PackageCache`) whose `.meta` guid is indexed so refs to it resolve, but whose contents are never parsed as a reference source.
- **guid-less node** — a real graph node with no guid (e.g. `ProjectSettings/*.asset`, a hand-authored `.uss` with no `.meta` yet). First-class in the walk.
- **builtin guids** — `0000000000000000e000000000000000` / `0000000000000000f000000000000000` families: Unity built-in resources. Display as "(Unity builtin)"; excluded from unresolved/broken accounting.
- **proven / advisory / speculative** — the confidence tiers an edge or answer carries; see Graph unification above.
